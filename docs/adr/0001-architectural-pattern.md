# ADR 0001: Выбор архитектурного паттерна (Clean Architecture + Feature-First)

## Статус
Принято (Accepted)

## Контекст
Приложению «Calista Tracker» требуется масштабируемая, строго структурированная архитектура с надежной изоляцией бизнес-логики. Согласно ТЗ и критериям оценки (25 баллов за архитектуру), необходимо четкое разделение на слои (данные, бизнес-логика, представление), обеспечивающее возможность изолированного unit-тестирования подсчета серий и уникальных алгоритмов без зависимостей от UI и локальной базы данных.

## Принятое решение
Использовать подход **Clean Architecture (Чистая архитектура Роберта Мартина)** с модульной организацией **Feature-First**:
- Каталог `lib/features/<feature_name>/` делится на три слоя:
  1. `domain` — чистые сущности Dart, интерфейсы репозиториев и сценарии использования (use cases). Нулевая зависимость от Flutter и сторонних SDK.
  2. `data` — таблицы Drift, DAO, мапперы и реализации интерфейсов репозиториев.
  3. `presentation` — экраны, виджеты, контроллеры состояния Riverpod.
- Общесистемные ресурсы (тема, дизайн-система, motion-токены, маршрутизация) выносятся в `lib/core/`.

## Рассмотренные альтернативы
1. **Традиционный MVC / MVP:**
   - *Плюсы:* простота начальной структуры.
   - *Минусы:* склонность к разрастанию контроллеров («Fat Controller»), сильная связанность бизнес-логики с жизненным циклом виджетов, сложность изоляции времени для unit-тестов.
2. **Layer-First Clean Architecture (папки data/, domain/, presentation/ в корне):**
   - *Плюсы:* явное разделение слоев на верхнем уровне.
   - *Минусы:* усложнение навигации по коду по мере добавления новых фич (код одной фичи размазан по всему дереву проекта).

## Последствия
- **Положительные:** 100% тестируемость слоя бизнес-логики чистыми юнит-тестами; независимость предметной области от способа хранения (Drift можно заменить без правки domain); соответствие требованиям ТЗ.
- **Отрицательные:** необходимость создания мапперов между моделями таблиц БД и доменными сущностями (небольшой оверхед по бойлерплейту, окупаемый надежностью).
